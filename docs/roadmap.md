## 〇、定位与六个环节
定位：统一系统观在 AI 辅助加持下的认知实践与自我进化（王总 2026-10-11 01:53 决定，出处同第 3 行）。定位句保留公开。
统一系统观的完整定义（王总 2026-10-11 07:18 确认，quote_ref grok-bot:t118u）及其要点：见内核（第十四节）。定义原文与要点属于内核，不在公开路线图中出现（quote_ref Grok Bot 转达·2026-10-11 22:51 SGT）。

工作流的六个环节见 docs/workflow.md：收集、消化、生产、发布、反馈、改进。

六个环节与定位的对应（协调 bot 推导，不是王总原话）：
- 收集、消化：为统一系统观提供观察材料。
- 生产：实践，按框架陈述事实并给出完全分类。
- 反馈、改进：自我进化，用台账证据修订框架版本（见第六节；闭环与三期安排见第十三节；框架版本在内核里修订，见第十四节）。

以下不属于王总决定：
- 发布：把通过审查门禁的实践结果公开。（bot 补写，待王总确认；确认前不生效：只是说明，不作规则使用）
- 审查不是六个环节之一，而是生产与发布之间的门禁，分工见第三节：脚本只负责格式与词表门禁，不批准任何稿件；每篇稿件都必须审查通过（稿件只有 Codex 结论为 APPROVED 才算通过；仅有 Codex 结论不等于通过）才可发布，需要王总批准的稿件类型（见第三节）还须经王总批准。
- 站点质检也不是六个环节之一，而是发布之后对线上页面的检查：审查决定一篇稿件能不能发，质检只看已经上线的页面有没有问题，分工见第二节。（bot 补写，待王总确认；确认前不生效：只是说明，不作规则使用）

**站点质检 bot 的职责与边界**（职责按王总要求，经 Grok Bot 转达，quote_ref Grok Bot 转达王总要求·2026-10-11 20:22 SGT；下面的检查口径、分派和分界细则，以及上表“禁止”栏里“只读、不直接改站点”以外的各项：bot 补写，待王总确认；从严临时执行，它们只增加检查，不放宽任何现行规则）：
- 审查管发布前，质检管发布后，两者不重叠。发布前归审查：第三节门禁，即审查与治理 bot 的格式与词表门禁加 Codex 审查，决定一篇稿件能不能发。发布后归质检：只检查已经上线的页面，不决定能不能发，也不改变任何门禁结论或批准记录。
- 质检查的是“线上页面对不对”：
  1. 中英两版：照 docs/i18n.md，已有英文版（*.en.md）的页面中英两版都已上线、能互相切换；没有英文版的页面，语言切换指向英文首页；tongyi 系列暂不出英文版，英文站不显示该栏目，不算缺版；
  2. 渲染：页面能打开，正文完整显示，没有原样露出的 Markdown、短代码或模板错误；
  3. 链接：站内链接和来源链接能打开；
  4. 引文：引文带出处链接，长度不超过第一节第 9 条的上限（中文 50 字，英文 30 词），线上文字与通过审查的版本一致；
  5. 写作规则：第七节写作纪律、第六节宏观措辞、第一节第 8 条中医与佛学规则中可以直接对照页面核对的条目；
  6. 免责声明：照 docs/i18n.md“免责声明”一节，文章页正文末尾有固定免责声明，非文章页不放；页脚投资提示照常显示。
- 质检不重做 Codex 审查：不判断事实对错、推断是否成立、翻译是否忠实，也不出 APPROVED、REJECTED 之类的结论。发现的问题需要这类判断时，Issue 里写明“需送审”，由负责的 bot 走第三节。
- 分给谁：页面内容、模板、发布与部署问题交生产与发布 bot；来源存档（raw/）缺失或对不上交采集 bot；脚本门禁该拦没拦的，交审查与治理 bot；拿不准归谁的，交 Grok Bot 协调分派。同一个问题已有未关闭的 qa Issue 时，只在原 Issue 补记，不另开。
- 修复与关闭：已发布页面的正文改动都是更正稿，照第三节重新取得 Codex APPROVED（需要王总批准的类型还须王总批准）后才能上线。修复上线后，质检 bot 复查；复查没问题才关 Issue，有问题就在原 Issue 写明，保持打开。
- 部署后冒烟检查（docs/smoke-check.md，CI 脚本）照旧运行。质检 bot 可以读它的报告作参考，但不代替它，也不改它。

两个角色需区分：“Grok/X 采集产出”指 markjin 采集 bot 通过 Grok 与 X 得到的内容，只是线索，任何断言都必须能回放到 arXiv 原文、FRED 序列等一手来源；“Grok Bot 协调 bot”只做协调与提醒，不产出内容，也不决定方向。方向变更由王总决定，Codex 只提审查意见。

## 三、审查路由（全站唯一规则）
- **现行做法**：门禁代码已随新 markjin-data 初始提交 c6df19a 迁入（规则与旧库一致）；站点发布尚未接入，接入前日报按人工流程发布（Codex 记录写在新 markjin-data，由审查与治理 bot 核对后合并）。
- **门禁分工**：审查与治理 bot 的脚本只负责格式与词表门禁（结构检查、直引核对、链接配对、硬拦词表、风险标注），不批准任何稿件；自检算出的 low_risk 与 R-* 只作 Codex 审查的参考，路由不读取（旧 markjin-data 仓库（已归档，不公开）的实现）。每篇稿件都必须取得审查通过（Codex 结论为 APPROVED）才可发布；有 Codex 结论但不是 APPROVED 的（含 APPROVED_WITH_FOLLOWUPS），按未获批处理。
- **取消低风险自动批准**（2026-10-11 王总定，quote_ref grok-bot:t161u，王总原话“1、行；2、按新写法，每天过codex”）：AUTO_APPROVED 路径永久关闭，任何稿件都没有免审或自动批准的路径；原“低风险判定”五步（含结构白名单、直引细则）不再决定能否发布。
- **按稿件类型的批准要求**（照站点 docs/i18n.md 与旧 markjin-data 仓库（已归档，不公开）的实现）：
  1. 日报（中文版与英文版）：Codex 审查通过（APPROVED），不需要王总批准。
  2. 英文版（*.en.md，任何类型）：一律须 Codex APPROVED（含翻译忠实性核对，R-TRANSLATION）；原稿类型要求王总批准的，英文版按原稿类型处理。
  3. 含推断或判断的非日报内容（包括“信号→瓶颈”卡）、宏观稿：Codex 审查通过（APPROVED）+ 王总批准。中医与佛学稿：Codex 审查通过（APPROVED），另须王总批准（bot 补写，待王总确认（从严临时执行））。
  4. 《统一系统观》系列（tongyi）：tongyi/<name>.md 的稿件（draft_id = tongyi-<name>）须 Codex 审查通过 + 王总逐篇批准（协调 bot 定，2026-10-11；照旧 markjin-data 仓库（已归档，不公开）的 route.py 与 docs/approvals.md）。该系列已按王总 2026-10-11 22:39 SGT 决定，经 Grok Bot 转达，quote_ref grok-bot:t212u，下架保存、转为内核，不再对外发布（第十四节）；本条照 route.py 现有实现保留，只作记录。
  5. Codex 参与生产的稿件，一律按“无审查路径”归档不发。
- **signal 与 tongyi 的批准记录**：信号卡（card_type = signal）和 tongyi 稿必须使用带 quote_ref、绑定 draft_id 的 v2 王总批准记录（schema_version 2），且 channel 必须为 direct（王总直接确认），逐篇绑定稿件；用 v1 记录 → E-ROUTE-RECORD-V2-REQUIRED，channel 不是 direct → E-ROUTE-RECORD-MISMATCH。日报类审查稿的 channel 接受 direct 与 via-grok-bot。
- **其他所有稿件**（上面没有列出的类型） → Codex 审查通过（APPROVED）+ 王总批准；Codex 参与生产的，按“无审查路径”归档不发。
- **分类不明 / 自检失败** → 当天不发布，在 review/ 记录错误码；无法判别是否含推断的，按分类不明处理。
- **路由判定顺序（唯一顺序，命中即停；照旧 markjin-data 仓库（已归档，不公开） PR #21 当时的 scripts/markjin/route.py 中 _decide() 的顺序；均为协调 bot 定（2026-10-10/11）；按 t161u 删去原第 6 步“低风险稿 → AUTO_APPROVED”，心跳与离线规则对每篇稿件生效，照旧 markjin-data 仓库（已归档，不公开）的实现）**：
  1. 输入、状态文件或批准记录不合法 → HOLD；已归档稿（含改名后同内容）→ 仍为归档，不复活；顺延稿在顺延当天（SGT）再路由 → HOLD。
  2. 硬拒内容 → 拒发；自检失败 → HOLD；批准记录读取或校验失败 → HOLD。
  3. 未到可发布日（未来日期稿；可发布日：普通稿为稿件日期，顺延稿为顺延日的次日）→ HOLD。
  4. 心跳新鲜且 mac_online=false → 当天归档，原因代码“Mac 离线”（优先于第 5 步的 07:00 顺延）。
  5. 已到可发布日 07:00（SGT）仍未发布 → 首次逾期顺延到次日；顺延稿再次逾期 → 归档，原因代码“未获批”。
  6. 心跳过期（state/publish-state.json 的 updated_at 超过 30 分钟；每次在王总 Mac 上跑完命令后写回）→ HOLD，可重试，不归档。
  7. 分类不明 → HOLD（取更保守的做法）。
  8. Codex 参与生产 → 归档，原因代码“无审查路径”。
  9. 批准校验通过（审查通过，见第二节，Codex 的 reviewed_at 不晚于可发布日 06:55；需要王总批准的类型还须有王总批准，recorded_at 同样不晚于 06:55；王总批准当天（SGT）有效；recorded_at 不早于 reviewed_at）→ 可发布。
  10. 批准校验未通过：06:55 前 → 待审（只有需要王总批准的稿件还要求王总在场；日报不检查“王总在场”，route.py 待生产 bot 同步）；否则顺延稿 → 归档（“未获批”），首次 → 顺延到次日。
  “当天”一律按 SGT（Asia/Singapore）日历日计算。代码只把 verdict=APPROVED 视为通过，与稿件口径一致。
- **王总缺席时（仅适用于 Mac 在线的日子）**：需要王总批准的稿件（含信号卡）没有王总批准就不发布，按顺延规则处理，只顺延 1 天，不再二次顺延；顺延稿当天未获批准就归档不发，原因代码“未获批”。日报只需 Codex APPROVED，不受王总缺席影响。王总缺席时不设代理人，任何 bot 都不得代王总批准或校准，只按停发和顺延规则处理。王总连续缺席超过 7 天时，由协调 bot 提醒。
- **归档**：归档是带原因代码的最终状态，原因代码包括“Mac 离线”、“未获批”、“无审查路径”等（顺延稿再次逾期归为“未获批”）。Mac 恢复后，已归档的稿件不得再作为可发稿。

## 四、每日时间线（SGT）
（王总要求 07:00 发布（quote_ref grok-bot:t130u），具体排期由协调 bot 定；2026-10-12 起生效。门禁只看两个时间点：06:55 批准截止、07:00 发布截止，到时没批准就按第三节顺延；05:20、06:25、06:30 只作排期，不作门禁；markjin-data route.py 的 CUTOFF=06:55、PUBLISH_DEADLINE=07:00 照此实现。站点质检的发布后逐篇质检和 07:20、20:30 两次全站巡查也不是门禁，不影响发布、顺延与归档。）

| 节点 | 时间 | 失败状态 |
|---|---|---|
| 采集 | 05:00、06:00 | 两轮都失败 → 当天无稿，记录 |
| 写稿与开 PR | 05:20 开始写，06:25 开 PR | 只作排期，不作门禁：没赶上不单独处理，仍按 06:55 批准截止与 07:00 发布截止判定 |

站点质检的安排（07:20、20:30 与逐篇质检照王总要求；以下细则：bot 补写，待王总确认；从严临时执行）：与新时间表同日（2026-10-12）起执行。巡查没跑成或延迟超过 30 分钟的，质检 bot 尽快补跑，并在结果里写明实际运行时间（SGT）；逐篇质检和两次巡查的结果都报给 Grok Bot 协调。

## 五、证据链格式（扩源前先落地）
每条断言写成：**来源**（URL/post id/序列 id + vintage）→ **存档**（raw 路径 + sha256）→ **断言**（只复述来源内容）→ **推断**（明确标注，可为空）。每篇稿件不论有无推断，都须 Codex 审查通过（第三节）；“推断”非空、“断言”中含来源自身的推断，或含复述式断言的，Codex 审查时逐条对照存档核对。审查与治理 bot 按第九节抽样规则重新对照存档复核断言，统计结果写入 review/。X 帖子始终只作线索，不能单独支撑断言。

- 按季读数判定的分支（如按“连续 N 个季度低于 L / 高于 U”判定的分支；分支条件本身随台账公开）的记法（登记部分：bot 补写，待王总确认；从严临时执行；判定部分：bot 补写，待王总确认；确认前不生效）：l_value、u_value 在登记时按 lu_basis_date 和 lu_evidence 算出并写定，window_quarters 同时写定，事后都不改；quarter_readings 在核对时填写，每个季度写成“季度:读数@data_vintage#raw 路径:sha256”并用英文分号分隔，按时间先后排列，例如 2026Q4:5.10@2027-01-20#raw/2027-01-20/fred/CHNGDPNQDSMEI.csv:<sha256>;2027Q1:5.32@2027-04-16#raw/2027-04-16/fred/CHNGDPNQDSMEI.csv:<sha256>；季度必须与 window_quarters 一一对应，读数单位同 unit、取自登记的 data_source，并按登记的 data_vintage 取数规则取版本；“季度:读数@data_vintage”中的 data_vintage 是该季实际用到的版本；每个季度的实际 vintage 与 sha256 必须能在 raw/ 的 MANIFEST 中找到对应原件，并能从该原件复算出该读数，缺 data_vintage、缺 sha256 或对不上的季度按缺数处理；lu_evidence 中算 L、U 所用的每个读数，照同一格式绑定 data_vintage 与原件 sha256，任一读数缺绑定，这一期不登记分支；这类分支 interval_* 填 NA，判定以 quarter_readings、n_quarters、l_value、u_value 按登记的 trigger_condition 复算为准；quarter_readings 里的季度数少于 n_quarters 或有缺数时，按内核宏观框架的写法这一期不分类，全部行记 TRIGGER_UNOBSERVABLE（数据未发布的记 DATA_UNAVAILABLE）。王总确认前，这类分支到期后只填 quarter_readings，check_result 保持 PENDING，不判 HIT、MISS 或其他结果。
- error_source 有多个原因时（bot 补写，待王总确认；确认前不生效）：取值只限“采集”“解读”“框架”，用英文分号分隔，主因写在最前，不重复，例如 采集;框架。
- check_result 逐行填写，同一篇稿件的各行按整篇结果唯一确定：
  - 未到期：全部行 PENDING，actual_branch 留空。
  - 恰有一支命中：命中行 HIT（actual_branch=是），其余行 MISS（actual_branch=否）。“命中”指该支登记的触发条件对实际取值成立：区间型分支看 actual_value 是否落在 interval_*（含端点开闭）内，按季读数型分支看 quarter_readings 按 trigger_condition 复算是否成立。HIT 只表示分类成立（事先写好的分支里恰有一支发生），不表示对当前或未来做过判断。判 HIT 之前先核对数据来源（bot 补写，待王总确认；从严临时执行）：actual_value 或 quarter_readings 必须取自登记的 data_source，且每个读数实际用到的 vintage 符合登记的 data_vintage 取数规则，evidence 或 quarter_readings 中记下的 raw sha256 能对上、可复算；来源、版本或复算有一项对不上，就不判任何结果，check_result 保持 PENDING，在当周周复盘里报出，数据核实后再核对，以免取错的数据恰好落进某一支被记成 HIT。
  - 没有任何一支命中（漏分类）：全部行 NONE_HIT（actual_branch=否）。
  - 多支同时命中（触发条件失效）：命中行 MULTI_HIT（是），其余行 MISS（否）。
  - 无法按所写条件判定（触发条件失效）：全部行 TRIGGER_UNOBSERVABLE，actual_branch 留空。
  - 到期时数据未发布：全部行 DATA_UNAVAILABLE，actual_branch 留空；数据发布后重新核对并改填。
- 登记：生产与发布 bot 在宏观稿发布时登记全部分支，check_result 记为 PENDING。
- 核对：审查与治理 bot 在 window_end 之后核对实际落入哪一支，并填写 actual_value、actual_branch、check_result、checked_by、checked_at、evidence。

1. 起草：每周日复盘时，反馈与改进 bot 从分支台账中挑出漏分类（NONE_HIT）与触发条件失效（MULTI_HIT、TRIGGER_UNOBSERVABLE）的记录作为证据，写成框架修订提案（proposal Issue），逐条引用台账行（draft_id + branch_order）。

- 分子：分母中，在王总指出的时间之前，质检 bot 已开出描述同一问题的 qa Issue 的个数，以该 Issue 的创建时间（换算为 SGT）为准。质检 bot 在王总指出之后才开的 Issue、或发现了却没开 Issue 的，不计入分子；拿不准是否同一问题的，按没先发现计。

- 数据来源：站点仓库的 Issue。质检 bot 开的 Issue 带 qa 标签（仓库现有标签）；王总指出的问题由协调 bot 记成带 wang-found 标签的 Issue（标签待创建），正文写明王总指出的时间（SGT）和对应的 qa Issue 编号（没有就写“无”）。王总原话与渠道照第七节的规定存放在本机私有记录中（不公开），写入权限也照第七节，仅限审查与治理 bot 与王总；协调 bot 只负责把原话、时间与渠道转交审查与治理 bot 写入，并在公开 Issue 里登记问题本身，不另设存放路径。公开台账 review/ 只写计数、比率和日期（第七节字段白名单）。
- 用途：只作诊断，不进入周状态判定，也不作第十节阶段条件或第十三节各期门禁的依据。

卡片审查量表（每项合格/不合格）：① 证据可回放：每条断言有来源与存档；② 忠实原文：断言只复述来源内容，无原文之外的内容；③ 推断已标注：推断已明确标注并与断言分开；④ 不含投资措辞；⑤ 不含框架文档中标为“猜想”或“待王总定”的内容。第 ⑤ 项按内容判定：同一猜想或待定内容经改写、去掉标签后仍算不达标；卡片不含任何框架内容时该项记为达标。五项全部为否决项，合格线为 5 项全部达标，任一项不达标即不合格。量表只用于质量统计，不能覆盖第三节、第七节等拒发规则。

抽样规则：按自然周统计，周一 00:00 至周日 23:59:59（SGT）。断言与卡片的抽样数均为当周总数的 10% 向上取整，最少 3 个；不足 3 个时全量检查。卡片质量计入卡片所属的自然周。该周周日 23:59:59 数据截止后，由审查与治理 bot 在下周一 09:00（SGT）前锁定当周抽样数和抽样卡；同一自然周的抽样、校准对象和补做期限都用这批锁定的卡。锁定失败或迟发时记错误码，补做窗口到周二 23:59（SGT）；以周二 23:59 截止时是否已补成判定：已补成的只记错误码，未补成的该周记为“流程失败”。卡片“当周总数”指当周已生成并进入审查路由的全部卡片（含已发布、归档与顺延的卡，不含未进入审查路由的候选草稿）。（总数口径：协调 bot 定）

最终有效评分：王总已校准或复核的卡，以王总结果为准；校准出现分歧后已按王总口径复核的卡，以复核结果为准；其余卡以自动评分为准；标为“待复核”的卡在复核完成前没有最终有效评分。被王总校准或复核覆盖的旧自动评分不得再参与判定。

周状态判定：每个自然周只处于一种状态，按以下顺序判定，命中即停：
① 已知违规：有稿件没有取得有效的 Codex APPROVED（需要王总批准的类型还缺王总批准）就发布、任一抽样卡的最终有效评分不合格、证据回放率低于 95%，任一成立 → “未达标”；
② 截至周二 23:59 仍未完成抽样与样本锁定，或校准包未发出 → “流程失败”：计算效果等同“未达标”，要重新计数，但不计为王总未校准；
③ 有待王总复核的卡 → “待复核”；
④ 有卡片但王总未在期限内完成校准 → “未校准”；
⑤ 确实没有断言，且没有需评判的卡 → “不适用”；
⑥ 其余 → “有效”。当周没有卡片时，卡片相关各项不适用，不影响判定。
暂定状态的更正：周三 23:59 定稿前，校准或复核结果改变了某张卡的最终有效评分时，按上述顺序重新判定该周暂定状态。
常规定稿：周状态在周三 23:59（SGT）之前只是暂定，过了这个时间就定稿。“待复核”卡的复核截止时间与校准相同（周三 23:59）；复核完成前不得采用被质疑的自动评分，该周也不得定为有效周；逾期未复核的周定稿为“未校准”。王总事后给出的复核或校准结果只记入记录，不把该周改为有效周；事后结果为不合格的，按事后更正处理。
事后更正：周三定稿后，如果有证据表明出现违规（例如第 2 阶段核查发现有稿件未经 Codex APPROVED 就发布），就把该周更正为“未达标”；更正记录保留原状态、证据和更正时间。尚未确认第 2 阶段的，重新计数；已确认的，由协调 bot 通知王总决定是否退回第 1 阶段，不自动退回。

连续计数：“连续 2 个有效周”之间最多只能隔 1 个“不适用”周；隔得更长，或者中间出现“未达标”、“流程失败”、“未校准”周，就重新计数；“待复核”周在定稿前不计入。取得第 2 阶段启动资格后、王总确认前，如果出现“未达标”、“流程失败”或“未校准”周（含事后更正），资格作废并重新计数；“不适用”周不影响资格。第 2 阶段经王总确认后：出现“未达标”周（含事后更正）时，由协调 bot 通知王总，由王总决定是否退回第 1 阶段，不自动退回；出现“未校准”周时，协调 bot 通知王总，连续 2 周未校准就暂停含卡片内容的发布，直到王总恢复校准，不自动退回第 1 阶段；出现“流程失败”周时，协调 bot 通知王总，发布不暂停（各稿件仍按第三节门禁），由王总决定是否退回第 1 阶段，不自动退回；“流程失败”周既不计入也不中断“连续 2 周未校准”的计数。（“流程失败”处置：协调 bot 定）

校准：王总确认每周亲自校准 3 张卡（quote_ref Grok Bot 对话·2026-10-10·“可以，我每周亲自校准 3 张卡片”）。流程：上一自然周的抽样卡锁定后，反馈与改进 bot 在周一 09:00（SGT）把校准包发给协调 bot（发送失败或迟发时记错误码，补发窗口到周二 23:59；补发后王总的截止时间仍是周三 23:59；超过补发窗口的，该周记为“流程失败”，不算王总未校准）；校准包包括从锁定样本里随机取的 3 张卡（不足 3 张就全取）和量表。协调 bot 转给王总，再把校准结果回传给反馈与改进 bot，由它交审查与治理 bot 记录。周日 18:00 只发周改进提案，不取卡。王总校准时逐张卡、逐个量表项记录“达标”或“不达标”，并各写一句理由。审查与治理 bot 只负责抽样、汇总和记录，不做人工判断。王总的校准结果与自动评分不一致时，以王总为准，重算当周卡片质量；王总判定任一张不合格，该周按周状态判定 ① 为“未达标”；定稿后才得出的不合格结果按事后更正处理。当周抽样卡多于 3 张时，未经王总校准的其余抽样卡按自动评分判定；只要王总校准的 3 张里有一张不一致（校准出现分歧），审查与治理 bot 只在王总已记录的量表条目可以照着执行时复核其余抽样卡，需要人来判断的标为“待复核”交回王总，按周状态判定 ③ 和常规定稿规则处理。不一致情况在 review/ 记录错误码和数量，并在周改进提案中提出量表调整。王总校准的截止时间是校准包发出当周的周三 23:59（SGT），之前可随时补做；逾期仍未做的，该周按周状态判定 ④ 记为“未校准”，不计入有效周。

### 13.1 闭环五步
1. **事先登记，写了不改。** 每篇宏观稿发布时，生产与发布 bot 把全部分支、触发条件和判错读数登记进分支台账（第六节）。分两类字段（区分：bot 补写，待王总确认；从严临时执行）：
   - 事先登记（发布时写定，事后不改）：framework_version、framework_sha256（framework_sha256 每期登记：王总已确认，quote_ref grok-bot:t214s1036，王总原话“同意：公开口径和分支条件，每期登记内核校验码，经我同意才向指定审阅人出示内核”，2026-10-11 22:55 SGT；framework_version 列入事先登记：bot 补写，待王总确认；从严临时执行）、branch_order、interval_*、trigger_condition、observed_variable、unit、data_source、data_vintage、window_start、window_end、n_quarters、window_quarters、lu_basis_date、l_value、u_value、lu_evidence。判错读数指的是“observed_variable 在 window_end 的取值”这一口径，口径在此时写定。
   - 到期填写的实际读数（window_end 之后由审查与治理 bot 写入）：actual_value、quarter_readings、actual_branch、check_result、error_source、checked_by、checked_at、evidence。
   登记后事先登记的字段不得修改；登记有误只能新增更正行并保留原行（更正行的写法：bot 补写，待王总确认；从严临时执行）。
2. **到期对账，记下对错和错在哪一环。** window_end 之后，审查与治理 bot 按第六节 check_result 规则核对。整篇恰有一支 HIT 记为对；NONE_HIT、MULTI_HIT、TRIGGER_UNOBSERVABLE 记为错，并在 error_source 字段写明错在哪一环（字段名与三类取值：bot 补写，待王总确认；确认前不生效）：
   - 采集：数据取错、漏取，或用错了 vintage；
   - 解读：稿件没有按框架写分支或触发条件；
   - 框架：数据和写法都没有错，是框架本身的分类漏了或写坏了。
   DATA_UNAVAILABLE 不记对错，数据发布后重新核对。同一篇稿件的各行填同一个 error_source。
3. **每周日复盘，出修订提案。** 反馈与改进 bot 在每周日复盘时（与第二节周日 18:00 的周改进提案同一次），从三处材料起草修订提案（proposal Issue）：分支台账里记为错的行（逐条引用 draft_id + branch_order）、读者反馈（feedback Issue）、王总每周校准的 3 张卡（第九节“校准”）。框架的实质修订仍必须有台账证据（第六节“修订流程”末句）；读者反馈与校准结果可以支持采集、写法、门禁、排期类提案，但单凭它们不能支持框架的实质修订（bot 补写，待王总确认；从严临时执行）。
4. **审查、确认，才升版，并写入版本记录。** 提案先过 Codex 交叉审查（规划文件的通过口径见第二节 Codex 段），再经王总确认，才升版并写入版本记录：框架修订按第六节“修订流程”升小版本，写入内核宏观框架正文及内核版本记录（第十四节）；纯措辞修订按第六节“纯措辞修订路径”，Codex 确认判定不变就可写入，不经王总确认（王总定的例外，quote_ref grok-bot:t162s784），不升版本号。动到第六节五层核心结构的，须王总亲口确认。
5. **采集、写法、门禁、排期也走同一流程。** 这四类工作流改动同样是“提案 → Codex 审查 → 王总确认 → 写入路线图、升路线图版本并记 CHANGELOG”，效果用 13.2 的四个指标衡量。每份提案写明它预期改善哪个指标，下一个统计周期对照实测（bot 补写，待王总确认；从严临时执行）。

**与站点质检的分界**（bot 补写，待王总确认；从严临时执行）：站点质检 bot 发现并跟踪的是线上页面的具体问题（开 qa Issue、修复后复查、没问题再关），属于日常修复，不是修订提案，不走本闭环的提案流程，也不能借此改动任何规则。同一类问题反复出现、需要改采集、写法、门禁或排期规则的，由反馈与改进 bot 在周日复盘时把相关 qa Issue 当作材料起草提案（与第 3 步的读者反馈同等对待），再照第 4、5 步走。qa Issue 不能单独支持框架的实质修订（与第 3 步一致：框架实质修订须台账证据）。
